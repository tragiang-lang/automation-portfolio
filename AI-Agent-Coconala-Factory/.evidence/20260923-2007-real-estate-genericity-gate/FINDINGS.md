# Phase 1.5 findings: real_estate genericity gate

No finding was worked around in engine code. Categories come from task §16.

| # | Finding | Category | Evidence | Recommended follow-up |
|---|---|---|---|---|
| F1 | The intent catalog is one global asset, and `registry.intentCatalog()` picks the latest id for **every** industry. Real-estate words (内見, 見学, 申し込み) are missing. Adding them means a new catalog version, and that version would also change matching and the `_meta.assets` trace for hair_salon/restaurant. The demo brief matches only through existing keywords (予約, 問い合わせ, 相談, アクセス, 営業時間). A requirement phrased as 「内見を申し込みたい」 would currently **not** match. | data modeling gap (engine design: no per-industry keywords) | `src/registry/registry.ts` `intentCatalog()`; `src/agents/orchestrator.ts:78-79` | `customer-intents-v2` (data only) plus a planned regression run for all industries, or per-industry keyword data (engine change, Phase 2) |
| F2 | `reservation-basic-v1` requires the SERVICES sheet, so real_estate gets an empty SERVICES tab it never uses. The generated `SETUP.md` tells the owner 「`SERVICES` シートにメニューを入力します」. That text is hard-coded in `src/generators/delivery.ts:100` whenever SERVICES is present. | genuine engine limitation (minor, docs copy) | `projects/2026/demo-real-estate/delivery/SETUP.md:52` | Make the SETUP line depend on `service-menu-v1` being selected, or take it from industry terminology (engine change, deferred) |
| F3 | The industry schema has no `assumptions` / `extensionPoints` fields. Zod strips unknown keys, so these sections in `real-estate-v1.json` stay in the asset (and its lock hash) but do **not** reach `analysis/industry-profile.json` or `DELIVERY.md`. The same content also appears in `risks`, which does propagate. | genuine engine limitation (schema) | `src/schemas/assets.ts` `industryAsset`; profile keys listed in the chat report | Add optional `assumptions` / `extensionPoints` to `industryAsset` (engine change, deferred) |
| F4 | The LINE customer reply 「ご予約リクエストを受け付けました…確定しましたら改めてご連絡いたします」 is hard-coded in `createReservation.ts:161`. It keeps request semantics (good), but the text cannot say 「内見予約リクエスト」. | future extension (copy via CONFIG label, like `labels.serviceList`) | `core-assets/gas-modules/src/actions/createReservation.ts:161` | New CONFIG label key in a compatible `createReservation` minor bump |
| F5 | The reservation datetimepicker carries only a date-time. The customer cannot say *which property* to view. | valid Phase 1 boundary | `workflow/workflow.json` entry `default` | `property-viewing-v2` |
| F6 | No property data exists (property_catalog = deferred). 「物件を探す」 is a URI button to the existing site (`links.propertySiteUrl`). The requirement 「物件一覧は既存のWebサイトで見られるようにしたい」 is logged as an unmapped assumption, because URI buttons are not intent-traceable. | valid Phase 1 boundary / data modeling gap | `analysis/industry-profile.json` `assumptions` | `property-catalog-v1`, `property-search-v2`; optionally an `open_link` intent |
| F7 | `reservation.capacity` counts parallel requests, not agents or vehicles. | future extension | `createReservation` v1 config keys | `agent-assignment-v2` |
| F8 | The workflow displayTexts are fixed per workflow (「お問い合わせ」, 「店舗情報」) while the menu labels are 「物件のご相談」 and 「会社・店舗情報」. Acceptable, just slightly generic. | future extension | `rich-menu/menu-config.json` | Per-menu displayText override (engine change, deferred) |
